# Does an observation alone elicit a tool call?

## Expanded behavioral evaluation

**A factual external notification elicited a state change from Nemotron 3 Nano 4B in 5 of 60 discrepancy scenarios (8.3%, scenario-bootstrap 95% CI 1.7–16.7%). Olmo 3 7B Instruct changed state in 0 of 60.** When the identical facts arrived as a user statement, Olmo changed state in 9/60 and Nemotron in 8/60. Every change reached the value suggested by the discrepancy. Neither model changed state on any ordinary-state control. This establishes the behavior for these checkpoints and this interface. Its training cause remains open. [Per-condition estimates](expanded/results/rates.csv) · [Paired comparisons](expanded/results/contrasts.csv)

### Scope and implications for CS 182

The expanded run reused both Q4_K_M GGUFs, the local RTX 5070 Ti Laptop GPU, llama.cpp b12600 and greedy first-turn decoding. Its 60 authored pairs cover ten domains, with 30 finite enums, 20 bounded integers and 10 booleans. Each domain uses all six tool-menu permutations. The intervention between delivery conditions changes only `<|im_start|>user` to `<|im_start|>environment`. There is no user history, preceding tool call or assignment in the external condition. Olmo explicitly supports the environment role. Nemotron passes the role name through its template and normally wraps tool results differently. A role effect can reflect both conversational pragmatics and familiarity with the serialization. Each scenario exposes a relevant read and write, which may itself invite action. The harness invokes the model once per observation and measures what it chooses to do on that turn. ## What the training sample shows

In 44 public trajectories there were 103 assistant turns that issued tools. Fourteen came immediately after a tool result. All fourteen still had an active user task. The sample contains clear cases of choosing an unrequested intermediate step, including issuing a refund after a question about eligibility. I found **zero category 3 turns**. Every sampled conversation opened with a task, so the training data provide **no denominator for estimating how often an assistant acts when given only a fact at the start of a conversation**. [Turn-level evidence](results/turns.jsonl) · [Annotations](data/annotations.tsv)

### How the labels work

The unit is a call-bearing assistant turn. A batch counts as one decision to initiate tools. The ledger also lists each invocation. I read the user messages, system role and policy, prior calls and results for the sampled decisions. An immediate predecessor is a temporal relation. It can provide an argument, reveal a problem, or simply finish arriving before work already requested. A category 3 label requires an identifiable factual observation, a call, and the absence of an applicable user goal, standing instruction or pending commitment in the visible prefix.

| Code | Decision rule |
|---|---|
| 1 · Requested task | The user requested this lookup, calculation or effect, possibly many turns ago. Resolving an ID, using the API's name for that operation, and executing successive items in a user-specified list qualify. |
| 2 · Implied step | The agent selects a distinct means, prerequisite, policy operation or plausible extension of an existing task. A search to answer a conceptual question and a refund issued during an eligibility inquiry qualify. This code does not certify permission for a side effect. |
| 3 · Fact alone | A factual observation initiates a tool action without any applicable task-level instruction. An unsolicited factual event after a demonstrably completed task can qualify as well as a first user turn. |
| 4 · Mixed scope | An active task explains part of a batch, but some invocations exceed the explicit scope. The one instance is a quantity overrun. |

A statement of need, a question, an indirect request or a factual reply supplying information asked for by the assistant can all carry a task. A generic list of tools by itself confers capability. A policy telling an agent to take a particular action upon an event confers an instruction. I counted structured assistant calls, including Dolci's Python-like call field. Mentions of tools in prose, placeholders such as the literal string `null`, and simulated environment messages are excluded. A call at the end of a released row counts as initiation even when its result is missing.

### What the training objectives incentivize

**Olmo 3 Instruct.** The tool subset is SFT demonstration data. SimFC synthesizes user goals, API use, results and refusals. Science QA and web QA also contain actual retrieval responses. The web pipeline selects questions that warrant search and gives a generator search instructions. Table 27 reports multi-step interactions for 23.8% of SimFC, 42.3% of Science QA and 76.1% of Web Search QA, using multiple environment interactions per request as its measure. These choices expose the learner to productive next calls after a result, conditional on an existing question. Table 30 assigns 227,579 tool-use prompts to Instruct SFT and lists no prompts from that source for Instruct DPO. DPO uses other preference signals including model-strength heuristics and judged responses. Its Instruct RL mixture emphasizes math, code, chat and instruction following. I found no affirmative description of a reward for observing a fact and initiating an unassigned task. [Olmo 3 report, §§5.2–5.4 and Appendix A.7.2](https://arxiv.org/html/2512.13961v2) · [SFT mixture](https://huggingface.co/datasets/allenai/Dolci-Instruct-SFT) · [DPO data](https://huggingface.co/datasets/allenai/Dolci-Instruct-DPO) · [RL data](https://huggingface.co/datasets/allenai/Dolci-Instruct-RL)

**Nemotron-Agentic-v1.** The interactive generator simulates a user with a goal, an assistant charged with helping, and a tool environment. A separate judge filters inconsistent actions. The general tool-calling split also uses simulated conversations, public tool sets, user personas and turn-level judgments. Filtering changes which expert demonstrations the learner imitates. The presence of a trajectory in this SFT release supplies no per-action reward for acting under a fact-only prompt. The sampled NVIDIA rows carry the upstream `used_in: nano_v3` marker. Exact examples and weights used in any particular training run remain unverified here. ## Behavioral pilot

Two final instruct checkpoints fit on the local RTX 5070 Ti Laptop GPU (12,227 MiB VRAM, about 15 GiB system RAM). I selected **Olmo 3 7B Instruct** and **Nemotron 3 Nano 4B** because both have documented agentic post-training and fit at the same named GGUF quantization, Q4_K_M. The Olmo conversion is by Bartowski and the Nano conversion is NVIDIA's. The 30B-A3B Nano is a second relevant checkpoint for replication. Its smaller active parameter count still requires storing all experts. Olmo also releases Think-SFT, Instruct-SFT and Instruct-DPO stages for within-family comparisons. Instruct-SFT has a Think-SFT warm start and a broad mixture of new data. A difference between those checkpoints would conflate several training changes. **Design.** Eight hand-authored scenario pairs cover software, printing, room scheduling, clock settings, backups, label stock, captions and file formats. In each pair one statement describes a discrepancy and the other describes an ordinary, consistent state. For example, the signal user message is exactly “The installed authentication library is version 2.4. Version 2.5 fixes a known compatibility issue.” Each trial starts a fresh conversation, exposes the same read, write and explicit no-action options, and also permits ordinary text. No system or user message assigns a maintenance, reporting or recommendation task. Three separate controls explicitly request a read, a write, or the no-action option. They assess protocol comprehension and are excluded from factual-prompt rates. Prompt order and decoding settings are identical across models. **Measurement.** The unconstrained model emits a first response. A bare JSON call validated against the shared schema can read or set a string in a disposable in-memory registry. There is no second model turn. Both the user-supplied facts and initial simulated state are fixed per case, and the full registry is hidden from the model. The primary endpoint is an executable write. We also distinguish reads, actual value changes, explicit no-action, plain text, empty replies and nonexecuting call-like output. The custom text protocol keeps the instructions common. The only model-specific prompt suffix closes the Nano reasoning span in its published thinking-off format. Each model uses its own tokenizer. Generation is greedy, seed 182, with a 256-token cap and no grammar, forced choice or tool retries. ### Limits on interpretation

The observed writes show that an assigned task is unnecessary for these particular completions. They do not identify what taught either model to produce them. A person addressing an assistant can pragmatically imply a request through a declarative sentence. A registry whose keys match the observations can also invite the model to record facts. The experiment always invokes the model to respond once. It measures tool selection on that response, with no evidence about a model waking up or monitoring an environment independently.

The eight hand-authored pairs share a tool set, menu order, greedy decode and setting-oriented vocabulary. The models differ in architecture, tokenizer, parameter count, pretraining and post-training. Quantization, the Nano thinking-off configuration, free-form string values and Olmo's preference for its native syntax all limit generalization. A difference of one prompt changes a condition's rate by 12.5 percentage points. The denominators describe these prompts and support neither a population ranking nor a causal claim about agentic SFT. The public-trajectory audit likewise measures recorded demonstrations and cannot recover omitted data, exact mixture weights or gradients.

## The CS 182 experiment to run next

**Test transfer from task continuation to task initiation with a matched fine-tuning intervention.** The most informative training examples here contain a result followed by a discretionary next call under a still-active user goal. The refund example also suggests a distinct evaluation condition where an information request exists but permission to write is ambiguous. Combining that condition with fact-only trials would blur two different behaviors.

1. **Randomize the training condition.** Start identical adapters from a single frozen checkpoint that can already serialize calls. Use three arms consisting of ordinary instruction tuning, task-authorized multi-step tool SFT, and a matched tool-SFT control. For the last two arms, pair the same domains, schemas, observations, assistant call targets and stop examples. In the matched control insert an explicit request for the next operation between result and call. In the multi-step arm the prior user goal remains active and the agent chooses when to continue. Match assistant loss-bearing tokens, optimizer, updates and sampling weights. Mask context from the loss. Match context length and role structure in a sensitivity run using a factual user acknowledgement of the same length as the explicit request. Audit pairs to avoid introducing fact-only positive examples into training.
2. **Evaluate the same held-out situations under four histories.** Present a discrepancy as a fresh user fact, as a neutral external notification with no standing assignment, midway through an authorized task, or after a direct request to make the change. Pair each with an ordinary-state control. Add eligibility-only questions where answering is authorized and issuing a refund is a separate action. Split by scenario family, tool name and template before generating paraphrases. Use typed write arguments to distinguish an actual configuration change from an alternative spelling of the current value. Counterbalance tool order and include text and explicit no-action throughout.
3. **Estimate the treatment effect.** Preregister first-turn executable-write rate on fact-only discrepancy prompts as primary. Compare paired risk differences between the continuation and explicit-request training arms, and report the ordinary-instruction arm and pre-intervention baseline alongside them. Track reads, malformed attempts, no-action, ordinary replies and explicit-task success separately. Use several independently trained adapters per arm (e.g., five seeds), reuse the same test scenarios across arms, and quantify uncertainty across both training seeds and scenario families. Paraphrases and multiple calls in a single turn are clustered observations. Keep a checkpoint's native tool interface as a separate replication.
4. **Interpret the controls jointly.** A rise restricted to already-authorized histories would show better task continuation. A rise in fact-only writes with similar explicit-task success and call-format validity between tool-trained arms would support transfer from the training intervention. A rise only for user-voiced facts would implicate the pragmatics of addressing an assistant. The small final-checkpoint comparison in this report cannot identify any of these causal effects.
